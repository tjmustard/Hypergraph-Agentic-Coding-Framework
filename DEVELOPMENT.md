# Development Notes

Hypergraph Agentic Coding Framework is built to handle specific workflows safely and efficiently. This document is a starting point for developers modifying the project, providing a compact orientation to the key project documents and repository organization.

**Development Workflow:**

This project uses `uv` as its strict package manager, and `python3` in every command.
- Use `uv add <package>` to modify dependencies.
- Use `uv run --locked pytest` to run the suite in `dev/tests/`. Running pytest by hand uses whatever `TMPDIR` you have, so set it to an on-disk directory when you iterate on a host whose `/tmp` is a small tmpfs. `uv run --locked pytest --lf` reruns the last failures. Its cache is `.pytest_cache/` at the repository root, ignored by git and shared by every run in the checkout: after a `check.sh` failure it holds the failures of the last pytest leg that ran (the 3.10 leg's, since every leg runs), and two seats working in one checkout share it.
- Before you commit, run the full check:
  ```bash
  bash dev/scripts/check.sh
  ```
  It runs `dev/tests/` under both interpreters, the uv-managed venv and a Python 3.10 (`$HACF_PY310`, default `/usr/bin/python3`), both under pytest-xdist. The 3.10 interpreter needs `pytest-xdist` and `execnet` at the lock's versions: the preflight fails, never skips, when it cannot import pytest, PyYAML and xdist, and then prints the exact install line. It then runs ruff on the Python files changed since the merge-base with `main`. Live tests (marker `live`) never run here.
  - **Output and logs.** Every leg runs, even after an earlier one failed, and check.sh exits 1 at the end when any leg failed (`❌  check.sh failed: <legs>` on stderr); the preflight and the temp and worker refusals still stop it at once, and exit 75 from a leg (host busy) stops it with 75. Each leg's full output goes to a log, and pytest's junit XML next to it, in a run dir `<log root>/<UTC %Y%m%dT%H%M%SZ>-<pid>` (mode 0700), where the log root is `HACF_LOG_DIR`, else `${XDG_STATE_HOME:-~/.local/state}/hacf/check-logs`; check.sh prints `==> logs: <run dir>`. It keeps the newest 10 run dirs and removes older ones one exact name at a time; anything else in the log root (other dirs, symlinks, files) is never touched. The terminal gets one short block per leg from `dev/scripts/summarize_pytest.py`: the status, exit code and counts, up to 20 failing or erroring test ids with the last 15 lines of each traceback, and the log and junit paths. A passing leg is two lines. With no junit XML (or one that does not parse), or a failing leg whose XML names no failing test, the block shows the log's last 40 lines instead; the ruff leg shows its log's last 40 lines on a failure. Skip reasons are in the log (or run pytest with `-rs`). `HACF_CHECK_VERBOSE=1` also prints every leg's full output as it runs, as check.sh did before; the release gate sets it, keeps check.sh's logs in its own work dir (`HACF_LOG_DIR`), and prints the same per-leg summary under its check step.
  - **Host lock.** check.sh, every `pytest` of this repository (from `dev/tests/conftest.py`), the release gate and `dev/openrig_compat.sh` / `dev/openrig_probe_record.sh` take one per-user heavy-job lock through `dev/scripts/host_gate.py` (it needs only the standard library; PyYAML, when present, reads `host.yml`), so one HACF heavy job runs on the host at a time. The order is memory first (wait until `MemAvailable` >= `HACF_HOST_MIN_MB`, default 6144, without the lock), then `flock` on `${XDG_STATE_HOME:-~/.local/state}/hacf/heavy-job.lock`, then memory again (below the floor: release and wait again). The wait is bounded by `HACF_HEAVY_WAIT_S` (default 3600; `--wait-s` on the CLI) and polls every `HACF_HEAVY_POLL_S` (10 s); while waiting it prints the holder (job, pid, cwd, how long) at most once a minute. When it runs out, the job exits **75**: the host was busy, retry later; it is never a test verdict. The holder exports a token, `HACF_HEAVY_LOCK_HELD`, so nested jobs (gate, then check.sh, then pytest) run inside the same lease; a token only counts when it matches the holder record (`heavy-job.json` beside the lock) and its pid is alive and an ancestor. `host_gate.py run --job <name> -- <argv>` runs any command under the lock; the child keeps the locked file descriptor, so a killed `host_gate.py` never frees the lock while its job runs, and SIGTERM/SIGINT/SIGHUP go to the child's process group. `python3 dev/scripts/host_gate.py status [--json]` shows the lock, the holder (or a `stale` record whose pid is dead), `MemAvailable`, the floor and the heavy processes that do not take the lock; `heavy-job.log` beside the lock has one line per acquire and release. A heavy process that does not take the lock (another project's pytest) never blocks: it only lowers check.sh's workers to `HACF_TEST_WORKERS_SHARED` (default 4) when `HACF_TEST_WORKERS` is unset. `HACF_HEAVY_LOCK=0` turns the pytest hook off for one run; `HACF_HEAVY_LOCK_PATH` moves the lock (tests use it, and a token issued for another lock file never counts under it). The lock is shared with `openrig/hacf/bin/hacf-host.py job run`, the scheduler `host_gate.py` is a client of, so every job queues a ticket under `HACF_HOST_STATE_DIR` and is admitted by declared RAM and GPU needs, per-rig priority tiers and backfill (`hacf-host.py job status` shows the queue).
  - **Workers.** By default both legs get a worker budget: half the cores, and no more than the available memory allows after `HACF_TEST_HEADROOM_MB`, at `HACF_TEST_PER_WORKER_MB` per worker, for two suites at once (the builder's and the auditor's). Both constants are in `dev/scripts/check_env.sh`, whose `hacf_worker_budget` computes `max(1, min(nproc / 2, (MemAvailable_MB - HACF_TEST_HEADROOM_MB) / (2 * HACF_TEST_PER_WORKER_MB)))` with integer division, counting a negative memory term as 0. `HACF_TEST_WORKERS=auto|<n>|0` overrides it, `0` meaning a serial run without xdist; any other value exits 2. check.sh prints the count and where it came from.
  - **Distribution.** The `--dist` mode is `HACF_TEST_DIST` in `dev/scripts/check_env.sh`. An `xdist_group` marker anywhere in `dev/tests/` requires it to be `loadgroup`, and `test_xdist_group_needs_loadgroup` enforces this. Even with no `xdist_group` mark, `loadgroup` is a different scheduler from `load`: xdist's `LoadGroupScheduling` subclasses `LoadScopeScheduling`.
  - **Test temp.** check.sh puts test temp in `HACF_TEST_TMPDIR`, else an inherited `TMPDIR` that is neither `/tmp` nor on a tmpfs, else `~/.cache/hacf-tmp/check` (under `$XDG_CACHE_HOME` when that is set). It refuses a dir inside the work tree. `pyproject.toml` sets `tmp_path_retention_policy = "failed"` and `tmp_path_retention_count = 1`, so a green run leaves no test dirs, a failed run keeps its latest failed tests' dirs, and a killed run keeps its locked `pytest-N` up to 3 days. check.sh reports those dirs at start and never deletes them; remove them by hand only when no pytest is running.
  - **While a check runs,** don't edit the work tree: each xdist worker snapshots the tree for the installer tests at its own first use (a session fixture per worker). xdist workers run a thread, and the PTY tests call `pty.fork()` inside them, which Python 3.12+ reports with a `DeprecationWarning`. It is harmless today; it matters if warnings become errors or a 3.12 leg is added.
  - **The timeout test.** `test_timeout_kills_process_group` (`dev/tests/engine/test_executors.py`) waits up to 30 s after `hx.run`'s group SIGKILL for the leader and the child to be gone, because under a full xdist load the kernel can deliver SIGKILL late to a task in uninterruptible I/O (D state). On timeout its failure names each pid's `/proc/<pid>/stat` state.
  - **Measured** (dev-test-speed slice 3, 2026-11-23, on a host with nproc 20, 10 workers): check.sh wall time went from about 946 s to about 122 s (B/A 0.131 and 0.129). CPU user+sys rose 19-20% (xdist overhead). Peak memory (the scope's `memory.peak`, page cache included) went from about 3.4 GB to about 2 GB. `--dist loadgroup` was about 14% faster than `load` (pytest 58.6-61.0 s per loadgroup leg against 68.4 and 70.4 s for the two load legs), which is why it is the default.
- **Test rig.** `dev/test_rig.py` runs one command against a throwaway rig launched from a copy of a project, as one job of the heavy-job scheduler (`hacf-host.py job run --job test-rig`, RAM = seats × the host config's `seat_ram_mb`, default 330), and always deletes that rig afterwards. It is dev only and never installed into projects. It starts real seats, so check that the host has room first.
  ```bash
  TMPDIR=~/.cache/hacf-tmp/test-rig python3 dev/test_rig.py run --project <root> --seats orch.lead,build.execute -- <test argv>
  ```
  - The project is copied to `$TMPDIR/hacf-test-rig-<stamp>/` (`TMPDIR` must be set, not `/tmp` and not inside the project). In the copy only, `openrig/hacf/rig.yaml` keeps the chosen members (default `orch.lead`) and the edges between them, and `rig spec validate` must pass. A full-size rig (every member) needs `--full --approval <qitem id>`, a queue row with the person's say-so.
  - The rig is named `hacf-test-<project>-<UTC stamp>`, never mapped in the host config, so auto-park leaves it alone. The command runs with `HACF_TEST_RIG=<that name>`, `HACF_TEST_RIG_COPY=<the copy's resolved path>` and `HACF_TEST_RIG_STUB=<the stub>`, no stdin, in your current directory.
  - **The stub destination.** A test rig's questions and updates stay inside it. Before the launch, the copy's `openrig/hacf/overrides.yml` gets `routing.question.destination` and `routing.update.destination` set to `{session: <stub>}`, the first chosen seat in the spec's order (`orch-lead@<rig name>` by default); its other keys are kept. The copy's `seat-config.py resolve --section routing` must then give that stub for both, or the run is refused (exit 2, nothing launched), as it is when `overrides.yml` cannot be read as a mapping. The run log names the stub. There is no opt-out. This covers routing only: a `rig send` or a row a seat addresses itself is not stopped, so tell the fixture's seats in its `CLAUDE.md` what they may do.
  - A copy that reaches outside itself is refused (exit 2, the path named, the copy removed even with `--keep-copy`): an absolute symlink, a symlink resolving outside the copy, or a `.git` file (a linked worktree or submodule). A project with a `.venv` has absolute links, so it is refused.
  - Afterwards, also on failure or a stop signal: a `rig up` that has not succeeded has its process group stopped (SIGTERM, 10 s, SIGKILL), then every open row (pending, in-progress or blocked) to the stub or from a seat of the run is closed as canceled and named in the log, then `rig down <name> --delete` (also when the list or a close failed), `rig ps` must no longer list it, no row of the run may be open, and the copy is removed (`--keep-copy` leaves it). The delete is refused for any name but the one this run generated and launched. Exit: the command's code, 1 when `rig up` failed, 2 on usage or a refusal, 3 when cleanup failed or was refused (the rows still open are named), 75 when the scheduler stayed busy.
  - The heavy lock is held until the cleanup has finished: `run` keeps `hacf-host.py job run` in its own session and relays SIGTERM, SIGINT or SIGHUP to the job's `_inner` process only (its pid is in `hacf-test-rig-<stamp>.inner.pid`). A stop while the job is still queued takes effect when it starts, so `run` waits until then (at most the scheduler's wait bound). A signal sent straight to `job run`'s pid still kills the job and frees the lock after 10 s (exit 137) while the cleanup may still be running.
  - The run's log is `$TMPDIR/hacf-test-rig-<stamp>.log`; its last line (`cleanup done` or `cleanup FAILED`) says how the run ended. A run killed outright (SIGKILL, a reboot) leaves its rig and copy behind.
- **Host sweep.** `python3 dev/scripts/host_sweep.py [--apply] [--json]` finds what killed runs leave on this host. It is dev only. Without `--apply` it only lists; `--apply` removes, signals and deletes, which cannot be undone, so read the listing first.
  - Run dirs named `openrig-compat-??????` directly under each dir of `~/.cache/hacf-tmp/`, `/dev/shm` and `/tmp`: stale when the pid in `state/owner.json` is dead, or with no owner record and an mtime over 24 h old. An unreadable record keeps the dir.
  - Your `openrig_compat.py listen` processes over such a run dir: stale when the dir is missing or its owner is dead. Each gets SIGTERM, then SIGKILL after 5 s, each only after its command line, run dir, uid and `/proc` start time are checked again (else `skip <pid>: not the listener`). A listener over a dir outside those places is left alone.
  - Test rigs: `rig ps` names that fully match `hacf-test-<project>-<UTC stamp>`, deleted with `rig down <name> --delete` when the stamp is over 6 h old. Any other `hacf-test-*` name is listed `not swept` and never deleted. It leaves the test rig's copies under `TMPDIR` alone.
  - Exit: 0 nothing stale (with `--apply`, all of it handled), 1 something stale or left, 2 usage, or `rig ps` could not be read. `HACF_SWEEP_ROOTS` replaces the places searched (for tests).
- **Advisor experiment (dev only).** `dev/experiments/advisor/run_arm.py` runs the advisor and `hacf-scout` helper experiment on throwaway test rigs: `gate`, `probe cli|mechanism`, `run`, `replay`, `score` and `report` (`--help` gives the exits). Only slice 13 of `v068-host-ops` (`13-advisor-run`, run by the lead) runs its probes, arms and replays, because they cost real money; the tests in `dev/tests/dev_experiments/` use fakes only. Arms 1 and 3 refuse to start until `probe mechanism` has passed. The **settings guard** hashes `~/.claude/settings.json` (and `settings.local.json`) before, during and after each run; on a change it stops the run, restores the file from its copy, writes `halted.json`, sends a row to the lead and exits 4, and the gate then says wait until the lead removes `halted.json`. The runner types no slash command into any seat. The planted defects are sealed outside the tree, in the private directory `run_arm.py` names; only their hashes (`sealed.sha256`) are committed.

**Git hooks:** the `pre-commit` hook blocks staged files under `spec/process/`, then runs `ruff check` and `ruff format --check` on the staged Python files only (added, copied or modified), and skips lint when `uv` is not installed. Never bypass a hook with `--no-verify`.

## OpenRig compatibility

HACF delegates `rig proof add` and `rig scope audit` to the versions of `@openrig/cli` listed in `.agents/config/openrig_contract.yml` (what a project sees is in [docs/OpenRig-Team.md](docs/OpenRig-Team.md#which-openrig-versions-hacf-uses)). Two dev tools decide whether a new version belongs in that file. Neither is installed into projects.

**The compat command.** `dev/openrig_compat.sh <version>` decides in minutes whether one `@openrig/cli` version works with HACF. It installs that version into a throwaway npm prefix under `$TMPDIR`, copies this tree (tracked and untracked non-ignored files, plus `spec/compiled/architecture.yml`) into the same temp dir, and runs there: the live contract suite (`dev/tests/contract/test_openrig_live.py`), the capture, `--help` and watched-file comparisons against the committed baselines in `dev/tests/fixtures/openrig-compat/<version>/`, the shipped range probe, HACF's `verify` and `proof` in delegate mode, and the openrig oracle (`dev/tests/openrig` and `dev/tests/installer/test_contract_pin_upgrade.py`). It never calls the host's `rig` and never touches a running rig: every candidate process runs with every `OPENRIG_*` and `RIGGED_*` variable dropped, `OPENRIG_HOME` and the caches under the temp dir, and `OPENRIG_URL` at a loopback listener the run opens itself, so any connection to it is a FAIL (`daemon-contact`). It lists the regular files directly in `~/.openrig/` (the daemon's logs and databases left out) before and after, and any change is a FAIL (`host-touched`). It writes only its own temp dir (a `mktemp -d` dir under `$TMPDIR`, removed on exit) and its evidence dir, `<evidence root>/openrig-compat-<version>-<UTC>/` (the evidence root is `HACF_COMPAT_EVIDENCE_ROOT` when set, else `${XDG_STATE_HOME:-~/.local/state}/hacf/evidence`); the one exception is the uv package cache, which stays the user's so the copy's venv needs no download. Without `--accept` it never writes the repo it runs from.
- **Before you run it,** set `TMPDIR` to an on-disk dir (it refuses `/tmp` and a tmpfs), check that `MemAvailable` in `/proc/meminfo` is at least 6144 MB, and run it in a memory-capped scope:
  ```bash
  systemd-run --user --scope -p MemoryMax=4G -p MemorySwapMax=0 -p OOMPolicy=continue \
    bash dev/openrig_compat.sh 0.7.22
  ```
  `OOMPolicy=continue` matters: with systemd's default, the first OOM kill stops the whole scope and no verdict prints; with it, the killed step is recorded and the run ends SETUP-ERROR.
- **Baselines.** A run compares against two committed baselines with the same `major.minor` and a version at or below the candidate: the newest one, and the newest whose contract entry is `accepted_by: person` (today they are the same). No baseline is a SETUP-ERROR that names `--seed`.
- **Verdicts and exit codes.** The last line is `openrig-compat <version>: <VERDICT> (<evidence dir>)`; on a FAIL it also names the failed step: `openrig-compat <version>: FAIL <failed_step> (<evidence dir>)`. A usage error exits 2 before any such line.
  - `0` **PASS**: every step green, and no watched file differs from either baseline. Help-text additions and new JSON key paths are reported, not failed.
  - `1` **FAIL**: a step is red; `failed_step` names it. A removed or renamed flag or subcommand in the help text is a FAIL.
  - `2` usage error or **SETUP-ERROR**: the harness failed (npm, the network, the disk, a signal, a timeout, an OOM kill), never reported as the product's failure.
  - `3` **REVIEW**: every step green, but a watched file differs (`lifecycle-manifest.js`, `mission-composition.js`, `scope-audit.js`, `scaffold-placeholder.js` and the four manifest templates).
  - `4` **SEED**: a `--seed` run that went green.
- **Reading the evidence.** `REPORT.md` is the human summary: the baselines and the integrity, each step with its result, exit code and time, then the failed step, the setup error and the watched-file differences when there are any. Help-text differences and new JSON key paths are only in `verdict.json`, which holds the full result as data (`version`, `verdict`, `failed_step`, `baseline`, `person_baseline`, `watched_diff`, `help_diff`, `json_paths_added`, `setup_error`, `timings`, `steps`, `integrity`, `problems`, and `accept` after an `--accept` run). `diffs/` holds each watched-file diff against each baseline, `logs/` each step's output, `steps.tsv` each step's exit code, time and OOM-kill count, `connections.log` and `openrig-home-before.txt`/`openrig-home-after.txt` the two isolation checks, and `baseline-candidate/` the normalised captures, help texts and watched files this run would commit as `dev/tests/fixtures/openrig-compat/<version>/`.
- **`--seed`** runs every step but the baseline choice and the capture and watched-file comparisons, so nothing is compared: SEED (exit 4) when green, never PASS. It makes the first baseline of a new `major.minor`; you commit its `baseline-candidate/` yourself.
- **A REVIEW** is accepted only through a reviewed commit: the reader writes `REVIEW.md` beside the new baseline (what changed, why HACF is unaffected, the evidence dir) and commits it with the baseline dir and the contract entry. `dev/tests/fixtures/openrig-compat/0.7.21/REVIEW.md` is the example.
- **The oracle's contract marker, and a missing watched item.** The oracle step and `--accept`'s own test run carry `HACF_COMPAT_WATCHER_VERSIONS`, the comma-separated `accepted_by: watcher` versions the run vouches for (the tree's own plus the candidate the harness just added); `test_contract_show` pins the person entries exactly and, with the marker set, tolerates exactly those watcher entries, so any other entry (or any entry without the marker) fails. A watched item that vanished or was renamed beyond its alias is REVIEW (`REPORT.md` names it as missing, and `meta.json` lists it in `watched_missing`); an item the harness could not read or a template it cannot parse stays SETUP-ERROR, and a `--seed` run stays strict.
- **The community-harness smoke.** `--harness <name>` (repeatable, default `agy`) picks the community harnesses the `harness` step checks against the candidate's own examples. Each ends in one of six statuses: `setup` (the checker could not do its job: SETUP-ERROR), `fail` (a preset, syntax check or launcher case is wrong: FAIL), `absent` (the package ships no example for it), `changed` (the example files differ from a chosen baseline's `harness/<name>/`), `unreferenced` (no chosen baseline holds it) or `ok`; `absent`, `changed` and `unreferenced` are REVIEW, so a version that ships no agy example is REVIEW `absent` (R137), and `--accept` needs every harness `ok`.
- `--registry <url>` installs from another npm registry. `--package-dir <dir>` installs a copy of an unpacked package instead (synthetic candidates for tests; its integrity is `local`; never with `--accept`). `--accept` is the watcher's, below.

**The daily watcher.** `dev/openrig_watch.sh` runs once a day under a systemd user timer. It uses no model and no tokens.
- **Schedule.** `hacf-openrig-watch.timer` fires at 06:20 local time, delayed at random by up to 15 minutes, and `Persistent=true` catches up on a missed day at the next login. Linger is off, so it runs only while you have a session on the host.
- **One run.** It asks npm for `@openrig/cli`'s `latest` version and for the `dist.integrity` of every accepted version. A changed integrity of an accepted version is a decision row (once per version and value); nothing is changed. A version already in the contract file, or one with a final verdict in the state dir, ends the run. Then the memory gate: the run starts only when `MemAvailable` is at least 6144 MB and no other pytest or `check.sh` of yours runs. It re-checks every 60 s for up to 30 min; if the gate never opens, the run is recorded as `deferred`. Then `dev/openrig_compat.sh <version> --accept --harness <name>...` runs on the watcher worktree, under `timeout`. A FAIL is retried once at once (the gate and the budget re-checked first; a closed gate or too little budget makes it `fail-pending`, retried the next day), and two FAILs are final. After any outcome, including every early exit, the run's tail runs (below); only a lock held by another run, or a state dir that cannot be created, skips it.
- **The budget.** One run has `--deadline <s>` (default 21000) and each compat run `--compat-max <s>` (default 5400). A compat run starts only when `deadline - elapsed >= gate_max + compat_max + 60 + 600`: before the first run that is a `deferred` run (`budget: <n>s left`), before the FAIL retry it is `fail-pending`. A compat run over its limit is a setup error.
- **Settings.** Optional settings, read from the env file (the installer writes each only when you pass its option). With no notifier and no row destination, the watcher calls no notifier, and its only `rig` call is `rig --version` (unless an upgrade destination is set).

  | Setting (installer option) | Default | Effect |
  |---|---|---|
  | `HACF_WATCH_NOTIFY_CMD` (`--notify-cmd <cmd>`) | none | each notification runs `<cmd> "<summary>" "<one line>"`; a command that does not resolve is logged and the run goes on |
  | `HACF_WATCH_ROW_DESTINATION` (`--row-destination <session>`) | none | each notification also sends one queue row to that session through the host rig |
  | `HACF_WATCH_HARNESSES` (`--harness <name>`, repeatable) | `agy` | comma list of the community harnesses each compat run smoke-tests; a bad name is a usage error |
  | `HACF_WATCH_UPGRADE_DESTINATION` (`--upgrade-destination <session>`) | none | where the upgrade request and withdrawal rows go; unset: no such rows, and `history.log` says `upgrade: no destination` |
  | `HACF_WATCH_FAILURE_NOTIFY_CMD` (`--failure-notify-cmd <cmd>`) | none | run as `<cmd> "<title>" "<line>"` when a watcher run fails (below) |
  | `HACF_COMPAT_EVIDENCE_ROOT` (`--evidence-root <dir>`) | `${XDG_STATE_HOME:-~/.local/state}/hacf/evidence` | where the compat runs write their evidence dirs (the watcher's `--evidence-root` wins) |
- **Each verdict.** Every notification prints one line, `notify: <summary> | <one line>`, to stdout (the unit's journal) and appends it to `history.log`, so the watcher is never silent. Then it goes to the configured notifier and to the configured queue destination, or, with neither set, only to the journal and the state dir. The queue rows and `rig --version` are the watcher's only `rig` calls.
  - PASS, a patch of an accepted minor: `--accept` commits the contract entry (`accepted_by: watcher`) and `dev/tests/fixtures/openrig-compat/<version>/` as one local commit on `swimlane/openrig-accepted`, after `uv run --locked pytest -q dev/tests/openrig dev/tests/installer/test_contract_pin_upgrade.py` passes on the tree to be committed. Row: `OpenRig <version>: accepted locally (watcher)`. A patch of an accepted minor is a plain `M.m.p` (no prerelease, `v` prefix or leading zero) whose `M.m` is accepted and whose patch is above every accepted patch of that minor: after 0.7.21, 0.7.22 is one; 0.8.0, 0.7.20 and 0.7.22-rc.1 are not.
  - PASS, but not a patch of an accepted minor: no commit; row `OpenRig <version>: not a patch: decision needed`.
  - PASS with the accept refused (`not-pass`, `not-a-worktree`, `wrong-branch`, `dirty-tree`, `head-moved`, `review-streak` when three watcher entries already follow the newest person entry in that minor, `tests-failed`, `commit-failed`, `error`, or `accept-missing` when the run left no accept result): no commit; a REVIEW decision row naming the reason.
  - PASS with `accepted-unexpected`: a commit was made, but it holds paths other than the two accept paths. The accept never amends or resets it, and the watcher sends the same REVIEW decision row, naming `accepted-unexpected`.
  - REVIEW, and a final FAIL: no commit; a decision row (`OpenRig <version>: REVIEW: decision needed`, `OpenRig <version>: FAIL: decision needed`).
  - SETUP-ERROR or SEED, and a failed npm or contract read: no verdict. The **first** setup error sends one row, `OpenRig watcher: checker broke`, or, when the compat run's cause starts with `harness:`, `OpenRig watcher: checker could not run the harness step on <version>` (that alone is no evidence that the checker is broken).
  - `deferred` (the gate stayed closed, or no budget was left): no verdict. The second run in a row without a verdict sends one row, `OpenRig watcher: <n> runs without a verdict`.
  - Each of these rows is sent once per stream until a run with a verdict resets it. The streams are `new-version` and `self-test`. `counters.json` is schema 2; the first run on a schema-less file moves its counts to `new-version`, clears every latch and writes `- counters-migrated <UTC> v1->v2` to `history.log`.
- **The tail,** in order: the installed version, the checker self-test, the upgrade reconcile, the host-change report, the "alerts dropped" row, and a final flush of the rows this run has not tried yet (skipped when under 120 s of the budget are left). The watcher only raises rows: it never upgrades, restarts or decides that a rig is idle.
- **The installed version.** `rig --version` is parsed into `installed.json`; the first one is recorded with no row. An unparsable answer defers the self-test.
- **The checker self-test** checks HACF's checker against a fresh npm copy of the installed version `I` (not the host's install): this run's compat result when it already ran on `I`, else a run without `--accept`. It compares `verdict`, `watched`, `help` (the baselines whose help diff is non-empty), `harness` and `baselines` with the expectation `selftest/<I>.json`. An expectation recorded before v0.6.8 (no `help_rule`) is re-recorded once. With none, or when the baselines changed, one is recorded from the first rule that applies: (1) `I` is in the contract with its own baseline dir: `PASS`, or `REVIEW` for the harnesses that dir lacks, with nothing watched or changed in help; (2) the watcher's own final verdict for `I`, unless it is a FAIL; (3) the first PASS or REVIEW result, marked unchecked. A recording is one row; a match is a history line only. A mismatch or a setup error is one `OpenRig watcher: checker broke (self-test <I>)` row until a match; a FAIL with no basis is one row per version and is never an expectation. A skipped self-test (version unknown, npm unavailable, budget, memory gate) is `selftest deferred: <why>`, with a row on the second in a row.
- **The upgrade request** (`upgrade.json`: the open request, the done versions, the owed withdrawals). A version is eligible when its final verdict is `accepted`, it is above `I`, this run's npm integrity equals the recorded one, its accept commit is on `swimlane/openrig-accepted`, and it is not done. At most one request is open, for the highest eligible version. Every run first re-checks it: fulfilled when `I` reaches it, expired after 7 days, withdrawn (`verdict-not-accepted`, `integrity-changed`, `accept-commit-gone`, `installed-at-or-above`, `superseded-by-<V>`) or, if `rig` never printed an id for it and it was never sent, dropped. When the version or integrity is unknown the request is kept, and an unsent one waits. A request or withdrawal is sent only from `upgrade.json` after that check, with `--verify`, never through the outbox; a failed one is re-sent with `--id` and the same body. An unreadable `upgrade.json` is left alone and the run exits 1.
- **The request row** (`--expires-at`, tags `openrig-upgrade,openrig:<V>`) has the key `owr-<V>-<accept sha>` and a **verify before acting** block, which stands in for authentication because the source label is only claimed: the evidence dir, the `verdict.json` sha256, its `PASS`, `accepted` and accept sha, the `git merge-base --is-ancestor` check, and the `npm view ... dist.integrity` to compare; then the condition (the openrig-upgrade path, when every rig's seats are idle), the rollback target and the expiry. The row destination gets a verified FYI row when a request is sent, withdrawn, dropped or expired, and `OpenRig host: <from> -> <to>` after a version change.
- **The outbox.** A row is written to `<state>/outbox/` before it is sent, and removed only when `rig queue create` exits 0. A failed row stays, with the request id `rig` printed; `history.log` gets `row-failed <UTC> <summary>`, `latest.md` is overwritten with it, and the run exits 1. Each run first re-sends up to 20 waiting rows, oldest first, with the same body (its last line is `First attempted: <UTC>`) and `--id`. The outbox holds 50: adding to a full one drops the oldest, logs `outbox-dropped <UTC> <summary>`, exits 1, and a later run that gets a row through sends `OpenRig watcher: <n> alerts dropped (outbox full)`.
- **A failed run.** The unit's `OnFailure=` starts `hacf-openrig-watch-failed.service`, which runs `openrig_watch.sh --failure-notify`: with `HACF_WATCH_FAILURE_NOTIFY_CMD` set, it runs `<cmd> "HACF OpenRig watcher: run failed" "<last line of latest.md>; see <state>/history.log"` and records the exit status in `history.log`; unset, it does nothing. A run fails when it exits non-zero or is killed. A desktop notification is **visible only while you are logged in** at the desktop (linger is off, and the notifier needs the session bus, which it may have to set itself); otherwise the failure stays in the journal and `history.log`.
- **The branch.** `swimlane/openrig-accepted` lives only in the watcher worktree. It is never pushed (the repository's pre-push hook, `.agents/scripts/pre-push`, refuses every `swimlane/*` branch). The lead merges its accept commits into a release line; a project gets a new version only through a later HACF release and its own upgrade.
- **A refused accept can leave a file behind.** If the accept's test run leaves an extra file in the watcher worktree, the accept is refused, but the file stays, so every later run reads `dirty-tree` until you remove it: check `git -C <watcher worktree> status` and delete what the test run left.
- **State.** `~/.local/state/hacf-openrig-watch/`: `latest.md` (one line: version, outcome, time, evidence), `history.log`, `verdicts/<version>.json` (final verdicts), `last-run`, `counters.json`, `installed.json`, `selftest/` (expectations), `upgrade.json`, `outbox/` (rows not yet sent), `run.log` (the last run's log), `lock` (one run at a time), and `last-compat.log` when a compat run left no evidence dir. A compat run's output is copied to `watch-compat.log` in its evidence dir. `journalctl --user -u hacf-openrig-watch.service` has the unit's own log.
- **The unit.** `dev/systemd/hacf-openrig-watch.service` is a template with no home path: `Type=oneshot`, `TimeoutStartSec=21600` (it covers the 21000 s run budget), `OnFailure=hacf-openrig-watch-failed.service`, `Nice=10`, `IOSchedulingClass=idle`, `MemoryMax=1536M`, `MemorySwapMax=0`, `OOMPolicy=continue`, `TMPDIR=%h/.cache/hacf-tmp/openrig-watch` and `XDG_CACHE_HOME=%h/.cache/hacf-openrig-watch`. `MemoryMax=1536M` is the floor the watcher's spec sets: one measured 0.7.21 compat run peaked at 415 MiB (the worst of five at 494 MiB), and 1.5 times that, rounded up to a multiple of 256 MiB, gives 768 MiB, below the floor (the unit file's comment shows the arithmetic). One 0.7.23 run with the harness step peaked at 462 MiB with no OOM kill (1.5 times that is 694 MiB), so the floor stands. The accept's pytest run also runs inside the unit and was not measured.
- **The env file.** `~/.config/hacf-openrig-watch/env`, written by the installer, is the only place the host's tool paths and settings live: `PATH` (npm's, node's, uv's and, with `--notify-cmd` or `--failure-notify-cmd`, the notifiers' dirs, then `/usr/bin` and `/bin`), `HACF_WATCH_RIG` (the host rig's absolute path), `HACF_WATCH_WORKTREE` (the watcher worktree), and the settings above when given. It holds no secret.

**Install, check, disable, remove.**
- **Run the installer from a login shell, not a seat,** for example your own terminal. Rig seats run with `DBUS_SESSION_BUS_ADDRESS=disabled:`; with that, or with `XDG_RUNTIME_DIR` unset or empty, install and `--uninstall` (with `--dry-run` too) exit 1 before they write or call anything. Install from a commit that holds the watcher scripts. The installer passes over a seat's `rig` shim (any `rig` whose realpath is under `/.openrig/run/seat-bin/`) and refuses when `PATH` holds no other; check `HACF_WATCH_RIG` in the env file afterwards.
  ```bash
  bash dev/openrig_watch_install.sh --worktree <watcher worktree> --base <commit> --dry-run
  bash dev/openrig_watch_install.sh --worktree <watcher worktree> --base <commit>
  # optional settings, for example a desktop notification:
  bash dev/openrig_watch_install.sh --worktree <watcher worktree> --base <commit> --notify-cmd notify-send
  # rows, a harness list and a desktop notification for a failed run:
  bash dev/openrig_watch_install.sh --worktree <watcher worktree> --base <commit> \
      --row-destination <session> --harness agy --failure-notify-cmd <cmd>
  ```
  It resolves `npm`, `node` and `uv` with `command -v`, and `rig` as the first executable `rig` on `PATH` that is not a seat shim, recorded as its realpath (any missing: exit 1, nothing written), and `--notify-cmd` and `--failure-notify-cmd` when given (unresolvable: exit 1, nothing written; a bad `--harness` name: exit 2), writes the env file, creates the watcher worktree with `git worktree add -b swimlane/openrig-accepted <watcher worktree> <commit>` when it does not exist (a write into the common `.git`), copies the three units to `~/.config/systemd/user/`, reloads systemd, enables and starts the **timer** (not the service), and runs the watcher's `--check-env` under the unit's env file; a failing check fails the install. With `--row-destination`, it then runs the watcher's `--row-check` under the unit's env file and `Environment=` (one real, verified queue row, no state written); if the row does not land, the install fails and prints the command to retry. It is idempotent and prints every path it writes. `--dry-run` prints the actions and changes nothing. A re-install fast-forwards an existing watcher worktree to `--base` (so the installed timer runs the new code from its next run) and refuses, before writing anything, a worktree with uncommitted changes or with local commits not in `--base`.
- Check: `systemctl --user list-timers hacf-openrig-watch.timer` shows the next run; `cat ~/.local/state/hacf-openrig-watch/latest.md` shows the last outcome once a run has happened.
- Disable, keeping everything installed: `systemctl --user disable --now hacf-openrig-watch.timer`.
- Remove: `bash dev/openrig_watch_install.sh --uninstall`. It disables the timer, removes the three units and the env file, and reloads systemd. It keeps the state dir, the evidence, the empty `~/.config/hacf-openrig-watch/` dir, and the watcher worktree with its branch, because they may hold accept commits nobody has merged yet; it prints the `git worktree remove` command for when they are merged.

**The limit: only `latest`.** The watcher sees only npm's `latest` dist-tag. A backport published after a newer minor, a patch skipped between two runs, and a rolled-back `latest` make no row. "No row" never means "no release": `npm view @openrig/cli versions` lists everything published.

## Telemetry

`dev/telemetry/collect_metrics.py` (stdlib only, Python 3.10+, never installed into projects) measures what a slice costs in tokens: per seat and per slice the fresh input, cache read, cache write and output tokens, their total, the cost-weighted total (fresh input ×1, cache write ×1.25, cache read ×0.1, output ×5), turns, the largest context and the wall time; per slice the escapes (`audit_failed` Outcomes lines plus later `HACF-Repin:`, `HACF-Block-Changed:` or `resolve: replan` commits naming it) and the rows sent to the advisor. Each run writes one `hacf.telemetry/v1` scorecard. It is read-only and exits 0 when a source is missing: the gap becomes a reason in `unknowns`, never a crash or a guessed number.
- **What it reads.** A snapshot copy of the OpenRig database (only the `usage_samples`, `context_usage` and `queue_items` columns it needs, never `queue_items.body` or `summary`); from the seats' Claude Code JSONL transcripts (and their `subagents/` files) only each assistant record's timestamp, request id, message id, model id and four `usage` counts, deduplicated by message id and request id; `git log` (commit times, subjects, trailers) and the slices' `PROGRESS.md`. **It never reads** message text, queue bodies or anything else in a transcript, never calls the network, and calls `rig` only as `rig whoami --json` when `--rig` is not given.
- **The snapshot rule.** The live database is never opened. The tool copies `openrig.sqlite` and its `-wal` and `-shm` with plain file reads into a private `snapshot-<UTC>-<pid>/` dir under the output dir, checks the copy with `PRAGMA quick_check` (one retry on a bad copy; a second failure makes the database numbers `unknown`), reads only the copy, and removes the dir before it exits. It never writes under `~/.openrig`.
- **Output.** `${HACF_TELEMETRY_DIR:-$HOME/.hacf/<rig>/telemetry}` (or `--out-dir`), mode 0700, files 0600. It is outside the repository and is **never committed**: it holds session ids. Slices are attributed by commit time: a usage record belongs to the first slice commit (`HACF-Slice:` trailer, or a `<mission> OPR.x.y.z:` subject) or `resolve:` compile at or after it; later records are `unattributed`.
- **Retention.** OpenRig keeps `usage_samples` 14 days by default. Sessions older than that have no samples and come out `unknown`, so record B0 promptly (by 2026-12-05 for v0.6.3).
- **B0, B1 and the verdict.** `--b0` (or `--b1`) writes one scorecard per window and `B0.json` (`B1.json`) with the median, n, min and max of the per-slice total and cost-weighted total (each `resolve:` compile split evenly over its mission's slices), the escapes per slice and the confounds (model ids and session counts per seat, context-guard restarts, the windows). `--compare` prints `met`, `not met` or `unknown` (n < 3) and writes `verdict-<UTC>.json`; the verdict is directional, not a release gate. The bounds are the lead's, from each window's first and last slice commit:
  ```bash
  python3 dev/telemetry/collect_metrics.py --rig hacf --b0 \
    --window v0.6.1=<first slice commit UTC>..<last slice commit UTC> \
    --window dev-test-speed=<…>..<…> --window v0.6.2=<…>..<…>
  python3 dev/telemetry/collect_metrics.py --compare <out dir>/B0.json <out dir>/B1.json
  ```
